# GMGN's query API: how it is called and what snipetech reads from it (12 Nov 2026)

## The answer first

**Reading does not need the destroyed private key.** A read is sent with the API key in one header, a timestamp and
a fresh id; nothing is signed. This comes from the source of GMGN's own command-line client (its `authExistRequest`)
and from GMGN's call-out page ("Read endpoints do not need `X-Signature`"). No real call with the owner's key was
made from here: the key lives only on the server. The first real answer is
`snipetech remote --wait run gmgn ping --json` after the deploy.

**Two reads are closed to us, and that is fine.** GMGN signs these with the private key, so our key cannot call them:

- a wallet's current holdings (`GET /v1/user/wallet_holdings`);
- the trades of the wallets our own GMGN account follows (`GET /v1/trade/follow_wallet`).

Everything else the owner asked for is open: the KOL and smart-money lists, a wallet's profit, win rate and history,
a coin's holders and traders with tags, trending coins, new pairs, candles, search by name. If holdings are ever
wanted, the owner would have to create a new key and keep its private half: do not do that for holdings alone, a
wallet's history (`wallet_activity`) answers most of it.

**GMGN never trades for us.** Every route that swaps, places or cancels an order, quotes a swap or creates a coin needs
the signature. `src/snipetech/gmgn.py` has no code for a signature and refuses any path that is not on its short list
of reads. The full map of GMGN's 19 skills, ranked by use, is `2026-11-12-gmgn-skills-map.md` (by a second helper);
this file is the HTTP side of it.

## Where this comes from

1. The public repository `GMGNAI/gmgn-skills` at commit `6a04e1f` (29 Oct 2026, client version 1.7.1), cloned into
   an empty scratch directory and read as text. Nothing in it was run or installed. `src/client/OpenApiClient.ts` is
   the HTTP client: host, paths, parameters, headers, signing. `docs/cli-usage.md` and the `skills/*/SKILL.md` files
   give options, weights and field tables.
2. `docs.gmgn.ai`: "GMGN Agent API" (setup only), "Generate Public Key", "GMGN Callout OpenAPI" (the one page that
   prints the host, the headers and the error format).
3. One request to `https://openapi.gmgn.ai/v1/user/kol` **without a key**, 12 Nov 17:00 UTC. It answered HTTP 401
   `{"code":401,"error":"AUTH_INVALID","message":"missing api key or client_id"}` with `x-ratelimit-limit: 5` and
   `x-ratelimit-remaining: 4`. So the host is up, the error shape is as documented, and the limit header is sent
   even on a refusal. This is the only real answer in the tests (`tests/fixtures/gmgn/error_auth_invalid.json`).

## How a call is made

| part | value |
|---|---|
| host | `https://openapi.gmgn.ai` |
| key | header `X-APIKEY: <key>` (on the server: `GMGN_API_KEY` in `/etc/snipetech/env`) |
| every request | query `timestamp=<unix seconds>` and `client_id=<a new UUID>`, on a retry too |
| clock | the timestamp must be within 5 s of GMGN's clock (client source; the call-out page says 15 s) |
| replay | an id seen in the last 7 s is refused |
| body | JSON on the few POST reads, `Content-Type: application/json` |
| signature | none on a read. Signed routes add `X-Signature` (Ed25519 or RSA of path, query, body, timestamp) |
| network | IPv4 only. A 401 or 403 with a good key usually means the request left over IPv6 |
| answer | `{"code": 0, "message": "ok", "data": ...}`; on a failure `{"code": <http status>, "error": "<CODE>", "message": "..."}` |

The client binds its connection to an IPv4 address, so the server cannot leave over IPv6. The key was created for the
server's IPv4; from any other machine GMGN answers `AUTH_IP_BLOCKED`.

Tags worth knowing. On a wallet (`tags`): `kol`, `smart_degen`, a trading app's name (`photon`, `axiom`, `gmgn`).
In one coin (`maker_token_tags`): `sniper`, `bundler`, `rat_trader` (an insider), `creator`, `dev_team`, `top_holder`.
As a filter on holders and traders (`tag=`): `smart_degen`, `renowned` (KOLs), `sniper`, `rat_trader`, `bundler`,
`dev`, `fresh_wallet`, `transfer_in`, `dex_bot`, `bluechip_owner`.

The fee presets sit under GMGN's trade path. It is a read (API key only, no wallet in it), the only one there, and
the client lets it through by its exact path as a GET; every other path with "trade", "swap", "order", "quote",
"strategy", "cooking", "create" or "follow" in it is refused before anything is sent.

## Limits

- Plans, rate and burst in weight a second: Free 5, Plus 20, **Pro 50**. Counted for the key and its IP together, so
  every job on the server shares one budget. The header `X-RateLimit-Limit` names the plan's number; `gmgn ping`
  prints it (50 means Pro answered).
- A 429 carries `X-RateLimit-Reset` (unix seconds) or `reset_at` in the body. `RATE_LIMIT_BANNED` lasts about 5
  minutes, and **every request during a ban adds 5 s**, up to 5 minutes (`RATE_LIMIT_BANNED_MAX`).
- `403 PLAN_UPGRADE_REQUIRED`: the route weighs more than the plan holds. Never retried.
- What the client does: spends 10 weight a second (`[gmgn] weight_per_sec`), waits out a limit of under 10 s once,
  and after a longer one sends nothing until the reset time.
- The hourly discovery run costs about 160 weight (2 lists, the trending list, 5 coins' traders, the profit of all
  wallets in batches of 100, 40 wallets' statistics): about 3 seconds of the Pro budget, spread over 16 at our pace.

## Finding people: what is there and what is not

- **There:** the wallets on GMGN's KOL list and smart-money list, as their newest 200 trades each. The list is
  whoever traded lately, so polling builds the set (the discover stage asks once an hour). Each trade carries the
  wallet's X handle and tags.
- **There:** search by name or X handle (`gmgn who Cupsey`); the winners of any coin with their tags and names;
  per wallet the profit over 1, 7 and 30 days and all time, the win rate, the X followers and how many GMGN users
  follow it (`follow_count`: how copied it is).
- **Not there:** a global leaderboard of traders, a pump.fun leaderboard, a list of all KOL wallets without their
  trades. GMGN's site shows such boards; this API does not serve them.

## What was built

- `src/snipetech/gmgn.py`: the client, one method a read; `snipetech gmgn <action>` (`ping`, `kol`, `smart-money`,
  `top-traders [mint]`, `who <name>`, `wallet <address>`, `fees <address>`, `created <address>`, `token <mint>`,
  `trending`, `new-pairs`, `candles <mint>`, `gas`, `signals`, `callouts`; `--raw` prints GMGN's answer as it came).
- `discover run` has a source `gmgn`: at most once an hour (`[gmgn] every_hours`) it puts the wallets on both lists
  and the winners of the 5 hottest pump.fun coins into `candidates` with their numbers. A wallet GMGN names gets a
  label: kind `kol` for a KOL, `wallet` for any other named wallet, source `gmgn`. A label somebody else wrote is
  never replaced. `[gmgn] label = false` switches the labels off.
- `doctor` has a row `gmgn`; the command is allowed as a server job and as an agent's job and holds no deploy back.

## Not verified (no key here)

1. **Every answer's field names.** The test answers are built from GMGN's field tables, not recorded. Where the
   tables disagree, both spellings are read (wallet statistics: `buy_count` / `buy`, `total_cost` / `bought_cost`,
   `winrate` / `pnl_stat.winrate`, `pnl` / `realized_profit_pnl`). The first `--raw` call of each action settles it.
2. **The unit of `priority_fee` and `tip_fee`** in a wallet's history, and of the fee presets. SOL is expected;
   nothing says so. `gmgn fees` prints them as sent and says "unverified". Check one trade against our own fee record.
3. Whether one `wallet_stats` request with several wallets says which row is which wallet. The client asks one
   wallet a request to be sure.
4. Whether `Pump.fun` is still the exact platform name (it is in every example); a wrong name may answer empty.
5. Whether the read-only key reaches the fee presets (they sit under the trade path) and the call-outs (the skill
   says the key must be bound to a GMGN account).
6. Whether the server's clock is within 5 s of GMGN's (`AUTH_TIMESTAMP_EXPIRED` would say so; the error text names it).
7. Rate limits beyond what the documents state; nothing was measured. The skills say an empty answer with a success
   status can mean "rate-limited", not "no data": an empty list from a busy route is worth one more look a minute later.
8. Whether GMGN's front door (Cloudflare) lets our HTTP library through. A plain `curl` got GMGN's own JSON; if the
   server's first `gmgn ping` says "HTTP 403, and the answer is not JSON", it is a block page and the client's
   `User-Agent` is the thing to change.

Pages that did not open from here: `https://gmgn.ai/ai` (HTTP 403 to the page fetcher), the npm page of `gmgn-cli`
(HTTP 403). The repository, `docs.gmgn.ai` and `openapi.gmgn.ai` opened.

## Text in GMGN's files that tells a reader to act (reported, not done)

The skill files tell an agent to run `gmgn-cli config --check` before anything, to ask the user for the API key and
apply it, to install the CLI with npm, and not to use web search or curl. None of it was followed: the files were
read as data, nothing was installed or executed, and no skill was added to any agent.
